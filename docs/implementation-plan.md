**Hard-won lessons (see commit history for full detail):**
- The `bpg/proxmox` provider's built-in `file_id`-based disk creation and its clone-time disk resize both route through a buggy conversion/resize path that reproducibly corrupted the guest filesystem (identical kernel panic, "Attempted to kill init!", every time — not a CPU or agent issue, despite those being tried first). Root-caused by manually reproducing each step outside Terraform with Proxmox's native `qm importdisk`/`qm clone`/`qm resize`, which don't have the bug.
- Fix: build the template disk via `qm importdisk` (a `null_resource` + `local-exec`, not the provider's native disk resource), pin clone disk `size` to match the template exactly (no implicit resize), then grow disks safely *after* first boot via `qm resize` (block-device-only, no partition rewrite) + in-guest `growpart`/`resize2fs`.
- `agent.enabled = true` hangs Terraform for 10+ minutes per VM since `qemu-guest-agent` isn't installed in the base Debian cloud image — left disabled for now (static IPs from cloud-init make it unnecessary so far).

**Hard-won lesson:** each VM independently downloading the ~80MB k3s binary from GitHub took 20-30+ minutes on this network — confirmed as a genuine link-level bottleneck (a Debian mirror and Rancher's own mirror were equally slow at the time), not GitHub-specific throttling. - [x] Real bulk storage — the earlier 29GB stick was a red herring; the user has since attached the actual drives: `sdb` (7.3TB NTFS, ~6.1TB used) and `sdc` (3.6TB NTFS, ~3.3TB used), both pre-populated with an existing media library (do not wipe). Mounted **read-only** on the Proxmox host via `ntfs-3g` (persistent `/etc/fstab` entries, `UUID=`-keyed) at `/mnt/media1` and `/mnt/media2`, then NFS-exported read-only (`/etc/exports`, `192.168.0.0/24`, `ro`).
- [x] ~~`nfs-subdir-external-provisioner`~~ — tried, then removed. It dynamically creates a *new empty* subdirectory per PVC; it can't expose an already-populated tree, and it needs write access to the export root to create those subdirectories, which the deliberately-read-only export blocks. The correct tool for "expose this existing read-only NFS tree" turned out to be app-template's built-in `type: nfs` persistence (mounts the export directly, no PVC/StorageClass/provisioner needed at all) — see Jellyfin's entry in Phase 6.
- [x] Tailscale subnet router (one node), advertising the MetalLB pool range — `infra/tailscale.tf`, runs as a systemd service directly on `k3s-control-plane` (not a k8s-native pod), advertises `192.168.0.240/28` (tightest CIDR covering the MetalLB pool). Route approved in the admin console and confirmed live (`192.168.0.240/28` shows in `tailscale status --json`'s `AllowedIPs`).
- [ ] Adguard Home configured as tailnet DNS — Adguard itself is deployed and DNS-tested working (Phase 6), but pointing the tailnet at it is a manual step in the Tailscale admin console (Settings → DNS → add `192.168.0.241`, enable override) that only the user can do
- [x] sealed-secrets controller — `bitnami-labs/sealed-secrets` has moved to `bitnami/sealed-secrets`; the old `bitnami-labs.github.io` chart repo URL now 404s, use `https://bitnami.github.io/sealed-secrets` instead
- [x] Wildcard TLS for `*.homelab.local` — the mkcert local CA from Proxmox/ArgoCD (Phase 3) now also covers ingress-nginx, set as its cluster-wide `default-ssl-certificate` (`infra/core-services.tf`), so every app's Ingress gets a trusted HTTPS cert automatically with no per-app config. **Side effect worth knowing:** ingress-nginx auto-redirects HTTP→HTTPS once a default cert exists, which silently breaks any automation still using `http://` (a POST returned a bare 404 instead of a redirect) — everything scripting against these apps needs `https://` now.

**Done when:** a test LoadBalancer Service gets an IP from the MetalLB pool, a test Ingress resolves, and a test PVC binds via NFS. ✅ Fully done — MetalLB/ingress/Tailscale/TLS verified, real NFS storage attached and mounted (Jellyfin actively using it, see Phase 6).

## Phase 6 — App rollout (in this order, per `design.md`) ✅ done

- [x] 1. Jellyfin — no official Helm chart exists; used `bjw-s-labs/helm-charts`' `app-template` (OCI, `ghcr.io/bjw-s-labs/helm` + `chart: app-template` — ArgoCD needs `chart` as a separate field even for OCI repos, `repoURL` alone isn't enough). Config on `local-path` (small, read-write). Media mounts the two real drives directly via app-template's `type: nfs` persistence — not a PVC/StorageClass, just a direct NFS mount, read-only (see Phase 4's storage entry for why `nfs-subdir-external-provisioner` doesn't work here). **Setup wizard completed via Jellyfin's own startup API** (`/startup/configuration`, `/startup/user`, `/startup/remoteaccess`, `/startup/complete` — lowercase paths; PascalCase 404s through this ingress), not the interactive UI. Automatic UPnP port mapping explicitly disabled. A `Videos` library (type `homevideos`, no metadata scraping) added pointing at both mounted drives, confirmed actively scanning. Credentials in `CREDENTIALS.md`.
  - **Gotcha 1 — config data loss on persistence restructure:** changing the `persistence` block's key names (removing `media`, adding `media1`/`media2`) caused the existing `config` PVC to get recreated rather than reused, and `local-path`'s default reclaim policy is `Delete` — so the admin account/settings were silently wiped. Caught immediately since nothing else was configured yet; redid the wizard. Worth remembering before restructuring `persistence` on an app with real data.
  - **Gotcha 2 — HTTP silently breaks after adding the wildcard TLS cert:** ingress-nginx's auto HTTP→HTTPS redirect (triggered by Phase 4's `default-ssl-certificate` change) turned a `curl -X POST http://...` into a plain 404 instead of a redirect, which looked like a routing bug rather than an HTTP-vs-HTTPS issue. `--ssl-no-revoke` + `https://` fixed it. This affects any future scripting against these apps.
  - **Gotcha 3 — Gotcha 1 recurs even on a purely additive `persistence` change:** adding a brand-new `newmedia` key (no renames, nothing else touched) still recreated the `jellyfin-config` PVC — confirmed via `kubectl get events`: a new ReplicaSet (`jellyfin-6c864d44f5`) replaced the old one and `jellyfin-config` went through a fresh `Provisioning`/`ProvisioningSucceeded` cycle (new PV, not the old one reused), wiping the admin account, the `Videos` library entry, and a just-created user. The actual media files were untouched (they live on the read-only NFS mount, outside the PVC), but Jellyfin's own config DB was gone, requiring the setup wizard to be redone from scratch and the whole ~9.4TB library to rescan. Root cause not fully isolated — suspect `app-template` hashes the *entire* `persistence` block into a pod-template annotation used for the rollout, so any edit to that block forces a new ReplicaSet regardless of which key changed. **Treat any edit to Jellyfin's `persistence` block as destructive to `config`, full stop** — not just renames. Do it during a low-stakes window, and re-verify Phase 7 backups exist before doing it again.
  - Also hit while redoing the wizard: `/startup/user` returned 404 with `{"Name":"admin","Password":"..."}` (PascalCase) but succeeded (204) with `{"name":"admin","password":"..."}` (camelCase) — `GET`/`PUT` on the same route both responded normally regardless of casing (ASP.NET routing is case-insensitive), so this was JSON body binding, not the URL, being case-sensitive for this endpoint specifically. Possibly version-specific (image tag is `latest`); check response bodies/`Allow` headers on a 404/405 before assuming the endpoint itself is gone.

## Phase 6+ — Additions beyond the original design

Added at the user's request, same patterns as the rest of Phase 6.

- [x] qBittorrent — `linuxserver/qbittorrent` via app-template. Web UI through ingress; the torrent port (6881, TCP+UDP) gets its own dedicated MetalLB IP `192.168.0.245` since it isn't HTTP. No inbound WAN peer connectivity — no port forwarding, per the CGNAT/Tailscale design — so this only works well for LAN/tailnet-initiated activity and outbound-initiated peer/DHT connections. Started with a temporary auto-generated password (from pod first-boot logs); permanent one set via `/api/v2/auth/login` + `/api/v2/app/setPreferences` (WebUI API, no startup-config endpoint like the other apps have, but this works and persists to the config PVC). Credentials in `CREDENTIALS.md`.
- [x] Whisparr — `ghcr.io/hotio/whisparr` (the community-standard image; `linuxserver/whisparr` and `thespad/whisparr` both exist but are stale, last updated 2022). Shares qBittorrent's namespace and downloads PVC directly (`existingClaim`) rather than needing cross-namespace volume sharing. Also mounts the existing media drives read-only so it can scan/match the library, though it can't reorganize or write into it.

- [x] Jellyfin metadata tagging — the "Videos" library (~5,530 items across both drives) had zero metadata beyond filenames, since `homevideos` type deliberately skips internet scraping (content doesn't match a movie/TV database). Wrote a one-off script against Jellyfin's own API (`Items` list → classify by path → `POST /Items/{id}`) to tag every item with a performer (`People`), studio (`Studios`), or category (`Tags`) based on two patterns actually present in the library: flat files named `YYYY-MM-DD Performer Name - Title.ext` (also sets `PremiereDate`/`ProductionYear` from the embedded date) and pack/collection folders (e.g. `Eva Lovia/`, `[Bangbros] Ass Parade 2004-2025/`), classified person-vs-studio-vs-tag via heuristics (bracket prefix → studio/tag, `.com`/`Siterip`/`MegaPack` → studio, camelCase mashed compound → studio, 2-3 space-separated capitalized words → person). 5,530/5,530 updated with 0 errors; Jellyfin's own name-matching quietly merged near-duplicate studio names (e.g. `Bangbros` and `BangBros` from two different folders) into one entity, so the final `/Studios` index shows 8 clean studios + dozens of tagged performers rather than the raw folder-name count. Read-only mount means only Jellyfin's own metadata DB changed — no files touched. A newly-added `RefreshLibrary` scheduled-task run was needed afterward for the `/Studios`/`/Persons` aggregate indexes to pick up the changes (individual items showed the new metadata immediately either way).
  - Purely heuristic, not exhaustive — folder/filename conventions vary a lot across sources, so some items may be miscategorized or left untagged. Good enough for browse-by-performer/studio and chronological sort; not meant to be perfect.
  - **Correction: People/Studios/Tags metadata alone isn't actually browsable.** `homevideos`-type libraries don't get the Genres/Studios/People nav tabs the web client shows for `movies`/`tvshows` libraries — that metadata was only reachable by clicking into an individual item or using search, not what "sort and categorize" actually needs. Fixed by creating a real Jellyfin `Collection` (BoxSet) per performer/studio/tag group (98 total, via `POST /Collections` + `POST /Collections/{id}/Items` for groups over 100 items) — Collections show up as a normal, clickable, always-visible library regardless of the parent library's type. This auto-created a new `Collections` virtual folder (`CollectionType: boxsets`) that **also needed adding to `raidi`'s `EnabledFolders`** (see the Jellyfin access split entry above) — it's a separate library from `Videos`/`New Videos` and isn't implied by having access to the items inside it. Verified by logging in as `raidi` directly (not just the admin account) and confirming the Collections view is non-empty.
  - **Collection thumbnails:** new Collections come with no image at all (`ImageTags: {}`) — Jellyfin doesn't auto-generate one on creation, and a full `Refresh` (`MetadataRefreshMode=FullRefresh&ImageRefreshMode=FullRefresh`) didn't produce one either. Fixed by copying one member item's already-extracted `Primary` image (`GET /Items/{id}/Images/Primary`) onto the collection itself (`POST /Items/{collectionId}/Images/Primary`, base64-encoded body, `Content-Type: image/jpeg`) — 98/98 set successfully.

- [x] Brute-force / rate-limit hardening, at the user's request — `nginx.ingress.kubernetes.io/limit-rps: "10"` + `limit-burst-multiplier: "5"` added to every app's ingress (throttles rapid repeated requests per client IP, login attempts included). Jellyfin's `LoginAttemptsBeforeLockout` set to `5` for both accounts (was unlimited). qBittorrent (`web_ui_max_auth_fail_count`/`web_ui_ban_duration`) and Nextcloud (core Bruteforce Protection) already had sane defaults, confirmed rather than changed. ArgoCD skipped — not exposed via ingress. **Explicitly declined** a request in the same batch to set every account's password to the same weak shared value — that would undo the point of having unique credentials (and a secrets manager) per service; offered to generate/rotate strong unique passwords instead if wanted.

**Real architectural tension worth flagging:** the whole point of Whisparr/qBittorrent is downloading new content and moving it into a media folder — which needs write access. The existing media drives are deliberately read-only (protecting the pre-existing library), and there's no other real bulk-writable storage attached. Downloads currently land on a small `local-path` placeholder (10Gi) — functional for testing, not sized for real use. Scaling this up needs either new dedicated write-capable storage, or a deliberate decision to make part of the existing storage read-write (a real tradeoff against the protection that read-only currently provides, not something to change casually).
- [x] HashiCorp Vault — official `hashicorp/vault-helm` chart, standalone mode, file storage backend on a `local-path` PVC, injector disabled (nothing consumes Vault secrets yet). Unlike every other app here, **not** auto-initialized — `vault operator init`/`operator unseal` is a manual one-time step (same "one manual seam" pattern as ArgoCD in Phase 3), and it comes back up sealed after every pod restart. Root token + unseal keys in `CREDENTIALS.md`.
- [x] Jellyfin access split — created a second Jellyfin user (`raidi`) and restricted them (`EnableAllFolders: false`, explicit `EnabledFolders`) to only the existing `Videos` library plus a new `New Videos` library (backed by the `newmedia` placeholder volume added to `jellyfin.yaml`, mounted read-write at `/media/new`). Intent: current content stays private to that one account, future additions (once dropped into `/media/new`) are visible to everyone. Note Jellyfin Administrators always bypass per-library restrictions, so `admin` sees both libraries regardless of policy — this only actually restricts non-admin accounts. Any future non-admin user must be created with `EnabledFolders` explicitly excluding `Videos`, since Jellyfin has no per-server default policy for new users. **This is also where Gotcha 3 above happened** — the `newmedia` volume addition wiped Jellyfin's config; see that gotcha for the recovery steps taken (redid the wizard, re-added both libraries, recreated the user).

## Phase 7 — Backup ✅ done

- [x] Chose Velero over Proxmox VM snapshots — this is a k8s-learning project, and Velero backs up/restores at the resource level (a single namespace or PVC, not "the whole VM"), which teaches more of the actual stack. Backend: self-hosted MinIO (`gitops/apps/minio.yaml`, official `charts.min.io` chart, standalone mode, `velero-backups` bucket auto-created via the chart's `buckets:` values field). MinIO's root credentials are a plain `kubectl create secret` (not a SealedSecret like Nextcloud's) — purely internal backup-system plumbing, and avoided installing `kubeseal` (small extra tool, not worth it here). `deployNodeAgent: true` + `snapshotsEnabled: false` — no CSI snapshot driver on local-path/NFS here, so Velero's kopia-based fs-backup is the only real option for PV data.
  - **Gotcha — chart's `upgradeCRDsJob` hook is broken, disabled it (`upgradeCRDs: false`):** the hook's init container `cp`-copies `/bin/sh` and `/bin/kubectl` from a `kubectl.image` into a shared `emptyDir` so the main container (`velero/velero`, which has no shell of its own) can exec them. The chart's default `docker.io/bitnami/kubectl:1.36` 404s — Bitnami stopped publishing plain version tags in favor of sha256-only digests (same pattern as the sealed-secrets chart repo move in `core-services.tf`), only `:latest` still resolves. Swapping to `rancher/kubectl` (Alpine/musl) failed too, silently, with the pod cleaned up before logs could be read (had to run the same image manually via `kubectl run` to catch the real error). Retrying with `bitnami/kubectl:latest` surfaced the actual problem: the copied `sh` needs `libreadline.so.8`, which isn't present in `velero/velero`'s image — the whole binary-borrowing trick is fragile across differing base images and there's no combination guaranteed to work. Not a real loss: the chart's standard Helm `crds/` directory installs all CRDs on first sync regardless of this hook — it only mattered for keeping CRDs current across chart *upgrades*, which barely applies to a homelab pinned to one chart version.
  - **Gotcha — a stuck ArgoCD sync operation ignores newly-pushed commits:** while debugging the above, each `git push` fix didn't take effect until the *entire* in-flight operation (all 5 retries) finished — a hard refresh (`argocd.argoproj.io/refresh: hard` annotation) updates the diff view but an already-running operation keeps retrying against the manifest it originally resolved. Had to let each retry cycle fully exhaust (or fail) before the next fix's commit actually got picked up.
- [x] Verified a real test restore, not just that a backup completes: created a `velero-test` namespace + marker ConfigMap, `Backup` (completed), deleted the namespace outright, `Restore` from that backup (completed) — namespace and ConfigMap data came back correctly. Cleaned up the test namespace afterward.

**Real limitation worth flagging (same one `minio.yaml` documents):** the backup target (MinIO) lives on the same node/disk as everything it's backing up. This protects against operator error, bad `kubectl apply`s, and broken GitOps syncs — not against actual disk/hardware failure, since there's no second physical disk in this homelab for real off-node backup. Revisit if one ever gets added.
