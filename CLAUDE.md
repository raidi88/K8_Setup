## Known gotchas (see implementation-plan.md for full detail)

- **Never let a VM disk get resized before first boot** — the `bpg/proxmox` provider's clone-time resize corrupts the guest filesystem reproducibly (identical kernel panic every time). `disk.size` in `infra/vms.tf`/`template.tf` must stay pinned to the template's native size (3G); real disk growth happens *after* boot via `null_resource.grow_disk` (`qm resize` + in-guest `growpart`/`resize2fs`).
- **This network is slow to GitHub-associated hosts specifically** (`github.com` release assets, `raw.githubusercontent.com`, `ghcr.io` all reproduced this; Debian/Rancher mirrors were fine). The fix pattern: download once to a local cache, verify checksum, distribute over the fast local LAN instead of letting every node hit GitHub independently (see `infra/k3s.tf`'s `k3s_cluster` resource for the reference implementation). Apply the same pattern if a future Helm chart/image pull from a GitHub-hosted registry hangs.
- Background `terraform apply` runs via this Bash tool can survive tool-call boundaries but not always cleanly — check `tasklist //FI "IMAGENAME eq terraform.exe"` and for stale `infra/.terraform.tfstate.lock.info` files if a plan/apply errors with a lock error after an interrupted run (delete the stale lock file, don't force-unlock a real lock).
